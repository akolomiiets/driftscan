# Unmanaged resources are a count from AWS Config

`driftscan unmanaged` reports, per resource type, how many AWS resources exist, how many some Root's state manages, and the difference. It is a number to watch over time, not a list of Findings to remediate: most unmanaged resources are legitimate (see noise below), so a per-resource alert would be ignored, and ADR-0006 rules out remediation anyway. The inventory comes from AWS Config advanced queries (`SelectResourceConfig`, or `SelectAggregateResourceConfig` with `-aggregator`) because one read-only call lists resource type, id and ARN for many types, across accounts and regions with an aggregator, without a per-service list call. It needs the Config recorder enabled for the counted types and the permission `config:SelectResourceConfig` (`config:SelectAggregateResourceConfig` for an aggregator). The managed set is built in memory from each Root's state (read-only, only `id` and `arn` attributes of managed resources are kept, ADR-0002) and ids and ARNs are kept in separate sets. A Config row with an ARN counts as managed only when its ARN equals a managed `arn`; a row without an ARN falls back to its resourceId equalling a managed `id`. Matching ids alone would let sub-resources that share a parent's name (an `aws_s3_bucket_policy` has the bucket name as id), same names across types or across accounts mark unmanaged resources as managed. Like `enrich` (ADR-0007) this is its own command: `scan` and `report` never call AWS.

## Consequences

- The recorder must be on and the Roots given must cover every state for the account; a missing Root shows its resources as unmanaged. A Root whose state cannot be read fails the run (exit 2) rather than inflating the count.
- Noise sources: resources created by AWS services (service-linked IAM roles, ENI-backed groups), by other tools, by CloudFormation or the console, and defaults (default VPC, default security groups). The default type list is small and avoids the noisiest types; users widen it knowingly with `-types`.
- Matching depends on the provider exposing the ARN in `arn`; types where Terraform's `id` differs from Config's resourceId (for example IAM roles) work because the ARN matches, and types whose state has no `arn` count as unmanaged whenever Config returns an ARN.
- A requested type with zero Config records produces a stderr warning (recorder off, type not recorded, or wrong region; IAM is recorded only in the home region), not an error. `-examples` lists the ARN, else the resourceId.
- The command exits 0 unless an error occurs (2); `-fail-over N` optionally exits 1 when the total unmanaged count is above N.
- Metrics: gauge `driftscan.unmanaged` with attribute `resource_type`, sent over OTLP/HTTP like the other metrics.
